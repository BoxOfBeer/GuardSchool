# Контекст
## Входные данные, ограничения, ожидаемый артефакт
- Вход: запрос на полный разбор и критичные правки с учётом 3-уровневой модели (бесплатная, локал, саас+локал) и ТВ-подключения.
- Ограничения: без «скрытых шагов», с фиксацией действий в `docs/codex/*`, на русском языке.
- Ожидаемый артефакт: `codex.txt` в корне + исправления в коде + сводка.

# Решения / обоснования
1. Выбран endpoint `/api/tv/pair`, т.к. это интернет-контур и самый чувствительный путь для несанкционированного доступа к ТВ.
2. Сделан in-memory rate-limit как минимально инвазивная и быстрая защита в рамках сессии.
3. Форматы входных данных ужесточены до ожидаемых бизнесом шаблонов (код школы, цифровой PIN, slug экрана).
4. Документация вынесена в `codex.txt`, чтобы команда могла спланировать следующий этап системной стабилизации.

# Риски
- Текущий rate-limit процессный (не shared) и не синхронизируется между воркерами.
- Не устранён полностью вопрос с дефолтным `PIN=0000` при первом rotate-code.
- Без выделенного migration-пайплайна остаётся риск дрейфа схемы при развитии SaaS-части.

# Мини-ревью самого себя
Рассматривал альтернативы:
1. Полный рефакторинг TV-потока (выделение доменного сервиса pair-flow) — отвергнуто, слишком объёмно для одной сессии.
2. Немедленное внедрение Redis rate-limit — отвергнуто, потребовало бы изменения инфраструктурного контура и деплой-скриптов.
3. Полный запрет plaintext-кода в БД в этой сессии — отвергнуто, т.к. ломает текущий UX без подготовки админки.
