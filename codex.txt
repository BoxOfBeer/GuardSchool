# Технический разбор GuardSchool (сессия 2026-04-18)

## Контекст архитектуры
Проект уже поддерживает гибридную модель:
1) бесплатный/локальный контур;
2) локал в сети школы;
3) SaaS+локал (тенант в SaaS, клиентские экраны в браузере/ТВ).

Для ТВ-подключения есть две стратегии:
- локальная (прямой /screen/<slug>);
- интернет-подключение через /t/<code>/<screen_slug> + PIN + device-token.

## Найденные проблемы и нестыковки

### Критичные (исправлены в этой сессии)
1. **Bruteforce риска на /api/tv/pair.**
   - До исправления endpoint позволял бесконечные попытки подбора code+PIN без блокировки.
   - При публикации в интернет это повышает риск компрометации доступа к экранам.

2. **Слабая валидация входных данных на /api/tv/pair.**
   - Не проверялся строгий формат кода и slug экрана.
   - Невалидный JSON мог давать нестабильное поведение при парсинге.

### Высокий приоритет (рекомендовано, не закрыто в этой сессии)
3. **PIN=0000 по умолчанию при первом rotate-code.**
   - Это удобство для старта, но в интернет-контуре создаёт окно риска.
   - Рекомендация: требовать явную установку PIN до выдачи активного pairing-кода.

4. **Хранение plaintext TV code в БД (`code_plaintext`).**
   - Это упрощает UX админки, но увеличивает цену компрометации БД.
   - Рекомендация: хранить plaintext только короткое время (TTL) или шифровать на уровне приложения.

5. **Нет централизованного персистентного rate-limit для multi-worker/горизонтали.**
   - Текущая защита in-memory, эффективна в single-process.
   - Рекомендация: перенести в Redis/PG таблицу лимитов.

### Средний приоритет (стабилизация)
6. **Неполный автоматизированный контроль слоёв (domain/infrastructure/ui).**
   - В текущей структуре нет формального import-linter контура из требований.
   - Рекомендация: добавить import-linter правила и сделать blocker в CI.

7. **Отсутствует единый реестр smoke-тестов для 3 уровней поставки.**
   - Рекомендация: минимальный сценарий на каждый уровень (free, local, saas+local) в docs/operations/BUILD.md.

8. **Нет формализованного процесса DB migration в ops/sql.**
   - Для текущего репо SaaS schema создаётся кодом (bootstrap), но требования заказчика подразумевают миграции как артефакты.
   - Рекомендация: ввести папку ops/sql и версионный runner.

## Что исправлено сейчас
- Добавлен базовый анти-bruteforce для TV pairing (окно попыток + временный бан).
- Добавлена строгая валидация формата `code`, `pin`, `screen_slug`.
- Добавлена безопасная обработка невалидного JSON (возврат 400).

## Рекомендованный план следующего шага
1. Убрать дефолтный PIN=0000 и пересобрать UX onboarding.
2. Вынести rate-limit в общее хранилище (Redis/PG).
3. Добавить миграционный контур `ops/sql/NNN_*.sql` + `schema_version()` и проверки клиента.
4. Добавить import-linter + ruff в CI как обязательный gate.
5. Формализовать smoke-тесты и build/runbook.
